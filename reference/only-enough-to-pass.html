Only enough to pass

The product change after one test is red. The test file does not change. Cases still on the list are not implemented yet.

The loop (this lesson)

  1. You already have one failing test of a tracer.
  2. Change the product so that this test passes, along with any tests you already had.
  3. Write only the code this test requires. Nothing from the rest of the list.
  4. Do not edit the test to make it pass.
  5. If you discover a new case, add it to the test list. Do not implement it yet.

Beck, Canon TDD, “Make it Pass.” Cleaning up the code after the test passes is a later lesson.

Which green move

Move What it verifies
Implement the rest of the feature Code the test did not ask for. Those parts were never forced by a failure.
Edit the test until it is green A pretend pass. Deleted assertions, or expected values pasted from a run, no longer catch a mistake.
Only the code this test needs Observed behaviour. The test is unchanged. The next case stays on the list.

The pass looks like

  • The same test file, with the same assertions you chose.
  • The smallest product change that makes those assertions true (for Handbook Ask, a stub that returns “I don’t know”).
  • No upload, real model, citations, or extra routes unless this test fails without them.
  • The tracer is still the destination. This green is not the whole tracer.
app.MapPost("/api/ask", (AskRequest req) =>
    Results.Ok(new { answer = "I don't know" }));

Done when

  • You can point at the same test and say it failed, then passed, without the file being edited.
  • The product change is only what that test required.
  • Other cases are still a list, not extra code and not extra tests.
  • An agent was told: only enough product code; do not edit the test; do not implement the list.

Agent prompt shape

The test is red. Do not edit it.

Write only enough product code to make THIS test pass.
Do not implement items still on the list: [cases].
Show me the passing run of the same test.
