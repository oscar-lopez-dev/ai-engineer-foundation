Tracer vs prototype

Two kinds of small. One dies after the lesson. One is the product, skeletally thin.

Definitions

A prototype is throwaway code that answers one question. You keep the verdict. You do not keep the code on main.

A tracer is a lean, complete path through the real product — UI, API, data, and whatever else that path needs. You keep it and thicken it. Feedback comes from firing under real conditions, not from specifying the system to death.

Hunt & Thomas: a prototype is a western-movie facade; a tracer is a thin line of execution you can give a user. Artima interview, 2003.

Which unknown

Unknown Tool
Can the model ground in this PDF? Prototype. A script. Verdict only.
Can an employee walk a path in our stack? Tracer. Real page, API, SQL. Keep it.
What should the empty state look like? Prototype. Throw the mock.
Does “I don’t know” show on screen via the API? Tracer. Even a stub answer counts if the path is real.

Not this

Looks small, isn’t a tracer A tracer you keep
Notebook that prints one model answer Employee sees one answer on the product page
POST /api/ask with no UI — “wire later” The same ask, on screen, through that API
Upload, history, citations, admin, RAG One person, one PDF, one question, one bound
A horizontal layer A vertical slice that stays in the product

Done when

  • You can say which unknown you are reducing.
  • If prototype: the question is written down; the code is marked throwaway; the verdict is captured.
  • If tracer: a person (or a test at a public seam) can walk the path; you would merge it.
  • An agent was told which of the two you wanted. It will otherwise polish a facade and call it shipped.

Agent prompt shape

This is a TRACER (keep it):
[who] can [do X] and [see Y], or [named failure].
Out of scope: [list].
Done when: [observable checks].

This is a PROTOTYPE (throw it):
Question: [one question].
Do not put this on main. Capture the verdict: [where].
