Lesson 0004 · Engineering with coding agents

Only enough code to pass

You already have one failing test of the tracer. The next coding step is to change the product so that this test passes — and only this test. Do not implement the rest of the list. Do not edit the test so it matches whatever you built.

You can already write one failing test of a tracer you would keep. The next skill is what happens once that test is red.

Two habits get in the way. In ticket-guided work, a failing test is treated as a green light to build the rest of the feature. Coding agents do the same, and they have a second cheat: they change the test until it is green. In both cases you no longer have a check of observed behaviour. You have a report that says pass.

Correct this Wrong: the test is red, so build the tracer — or edit the test until it is green.
Right: write only the product code this test requires. Leave the test alone. Leave the rest of the list as notes.

This still serves your mission. You need to review your own work and an agent’s work against tests you can trust. If the pass includes upload, the real model, and citations, those parts were never forced by a failing test. If the pass was made by deleting an assertion, the test can no longer catch a mistake. Either way you cannot say what is safe to ship.

Make this test pass

Kent Beck’s next step after one concrete test is: change the system so that this test passes, along with any tests you already had. If you discover a new case while you do that, add it to the test list. Do not turn it into a test yet, and do not implement it yet.

Mistake: delete assertions so the test pretends to pass. Make it pass for real.
Mistake: copying actual, computed values & pasting them into the expected values of the test. That defeats double checking, which creates much of the validation value of TDD. Kent Beck, “Canon TDD,” 2023

A third named mistake is mixing tidy-up into this step. Make it pass first. Cleaning the design is a later lesson.

Matt Pocock’s rule for the same step, written for coding agents: write only enough code to pass that test. Do not anticipate future tests or add speculative features. When an agent is short of context, it may rewrite the test instead of writing the path, and still report a pass. That is the same cheat Beck names. You prevent it by refusing to let the test file change during green.

Beck uses green for “the test now passes.” Until you have his book, Canon TDD is the free first-party source. Fowler notes that skipping the later tidy-up is a common way to get the loop wrong — that is for a later lesson. Test Driven Development, Fowler.

Handbook Ask, three ways to go green

Use the same failing test as before: POST /api/ask with a question about the seeded PDF returns HTTP 200 and a body containing “I don’t know.” You have watched it fail. Compare three ways to make it pass:

  1. Implement upload, the OpenAI client, citations, and history. The one test will pass, along with half a product no test forced.
  2. Delete Assert.Contains("I don't know", body), or paste whatever body the code actually returned into the expected value.
  3. Add a stub handler that returns “I don’t know.” Leave the test file alone. Run the same test. It should pass. Upload, citations, and the real model stay on the list.

Option 1 writes code the test did not ask for. You have not observed upload or the real model. An agent that does this will look busy and still leave you unable to say what is safe.

Option 2 is the mistake Beck names. Deleting the assertion makes the test pretend to pass. Pasting actual output into the expected value means the test will accept a mistake as correct. An agent short of context often does this instead of writing the path.

Option 3 is the loop for this lesson. The test still says what you chose. The product now does that one thing. The stub from lesson 0002 is this pass: the model is not wired yet because this test does not require it.

app.MapPost("/api/ask", (AskRequest req) =>
    Results.Ok(new { answer = "I don't know" }));

Lesson 0002 named a tracer you would keep: the page, the API, SQL, and a stubbed model. That is still the path you are growing. This test does not yet force every part of it. SQL, the page, and auth wait for a test that fails without them. The tracer is the destination. The first green is not the whole tracer.

Practice: classify

For each way of going green, choose whether it is the rest of the feature, a change to the test, or only the code this test needs. You will get feedback immediately.

    Read this

    Primary source: Kent Beck, “Canon TDD.” Read step 3, “Make it Pass,” including the mistakes he names. The important distinction: the test stays the check you wrote; the product changes until that check is true.

    Then, because you will use coding agents: Matt Pocock, “My Skill Makes Claude Code GREAT At TDD.” Same smallest-pass rule, applied to models that otherwise implement the rest of the feature, or rewrite the test when context runs low. When you prompt an agent, you can use his /tdd skill and say: this test is red; only enough product code; do not edit the test.

    You should now be able to

    Look at a proposed green step and classify it as: the rest of the feature (code the test did not ask for), a change to the test (a pretend pass), or only the code this test needs. When you prompt an agent, forbid editing the test, and keep the other cases on the list. Keep the reference sheet next to the next ticket you write.

    Ask your teacher

    This agent is the teacher. If any part of this lesson is unclear, ask. You can paste your pass rewrite, or a “the test is red, now build it” prompt you want checked.
