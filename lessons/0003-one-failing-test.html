Lesson 0003 · Engineering with coding agents

One failing test, not a suite

Once you have a tracer you will keep, the first coding step is one automated test of that path. Write the test so that it fails. Then write only the product code needed to make it pass. Do not implement first and add tests later. Do not write a full suite of tests before any code exists.

You already know a layer from a slice, and a prototype you throw away from a tracer you keep. The next skill is how to verify the tracer.

Two common habits get in the way. In ticket-guided work, people often write the code first and add tests afterwards. Coding agents often do the same, or they write many tests up front and then implement until those tests pass. In both cases the tests describe behaviour that was guessed, not behaviour that was observed.

Correct this Wrong: implement the tracer, then add tests — or write every test, then implement.
Right: write one test that fails, then only enough product code to make that test pass.

This still serves your mission. You need to review your own work and an agent’s work against tests you can trust. If the tests are written after the code, they tend to repeat whatever the code already does. If many tests are written before any code exists, they describe a design that has not been tried yet. Either way, an agent can change a test to match poor code and still report that everything passed. A single test that you watched fail, then pass, is harder to fake.

One test, then code

Kent Beck describes test-driven development as a short loop. First you write a test list: a scratch list of cases you expect to cover. That list is notes, not test code. Next you turn exactly one item on the list into a real, automated test. Then you change the system so that this test passes, along with any tests you already had.

Mistake: convert all the items on the Test List into concrete tests, then make them pass one at a time. What happens when making the first test pass causes you to reconsider a decision that affects all those speculative tests? Rework. Kent Beck, “Canon TDD,” 2023

So: the list is planning. The first real test is how a caller will observe the path (for Handbook Ask, usually an HTTP request). You write product code only after that test fails. Martin Fowler makes the same point: writing the test first forces you to think about how the code will be used, not how it will be built.

In Beck’s book the colours are a shorthand: red means the test fails; green means it passes; then you may tidy the code. That last step is for a later lesson. Until you have the book, Canon TDD is the free first-party source. Test-Driven Development: By Example, Beck.

Handbook Ask, three first coding moves

Use the same tracer as before: an authenticated employee pastes a question about the one PDF already in SQL and sees “I don’t know” on the real page. The model may be a stub. Compare three ways to start coding:

  1. Implement the page, the API, and the stub. Then write tests that match the responses.
  2. Write tests for upload, citations, history, auth, empty input, and OpenAI errors. Then implement until they all pass.
  3. Write one xUnit test: POST /api/ask with a question about the seeded PDF returns HTTP 200 and a body containing “I don’t know.” Run it and confirm it fails. Then write only enough ASP.NET code to make that test pass.

Option 1 writes tests after the code. Those tests will describe whatever was already built, including mistakes. You never confirmed that the test can fail. An agent that wrote the code first can make any assertion pass.

Option 2 is the mistake Beck names, and what Pocock calls horizontal slicing: many tests written at once check imagined behaviour. The extra cases (upload, citations, history) are still only a list. If you turn them all into tests before any path exists, you lock in a design you have not tried. When an agent is short of context, it may change a test instead of fixing the path, and still report a pass.

Option 3 is the loop for this lesson. The test states the tracer in a form the test runner can fail. If the route does not exist, you should get a failure such as HTTP 404. That is a real failure. After you add a stub that returns “I don’t know,” the same test should pass. Upload, citations, and the real model stay on the test list. They are not tests yet.

[Fact]
public async Task Ask_seeded_pdf_says_i_dont_know()
{
    var res = await client.PostAsJsonAsync(
        "/api/ask", new { question = "What is the leave policy?" });
    var body = await res.Content.ReadAsStringAsync();
    Assert.Equal(HttpStatusCode.OK, res.StatusCode);
    Assert.Contains("I don't know", body);
}

This test uses a public boundary: the HTTP API. It does not call a private method, and it does not mock an internal client. The expected values are ones you chose — the string “I don’t know”, and status 200 — not values copied from a passing run. Beck warns against pasting actual output into the expected values, because then the test can no longer catch a mistake.

Practice: classify

For each first coding move, choose whether it is many tests first, code first, or one failing test then code. You will get feedback immediately.

Implement POST /api/ask with the stub, then write tests that match the responses.

Write tests for upload, citations, history, auth, empty input, and OpenAI errors. Then implement until they pass.

One test: asking about the seeded PDF returns “I don’t know.” Confirm it fails. Then write only enough code to make it pass.

Scratch list: I don’t know, unauthenticated, empty question. Turn only the first into a failing test, then make it pass.
