Lesson 0005 · Engineering with coding agents

The next test, not the rest of the list

You already made one test pass with only enough product code. The next coding step is not the rest of the cases, and not the rest of the product. Look at the tracer you named. Write one new test of the part that still has no check. Watch it fail. Existing tests stay green.

You can already write one failing test, then only enough code to pass it. The next skill is what happens once that test is green.

Two habits get in the way. In ticket-guided work, one passing check is treated as permission to build the rest of the feature. Coding agents do the same, and they have a second shortcut: they turn the leftover cases into a suite. In both cases you leave the loop. You no longer have one new check of observed behaviour. You have a plan to finish everything.

Correct this Wrong: the first test is green, so write the remaining tests — or build the product.
Right: write one next failing test of the tracer you already named. Existing tests stay green. The rest of the list stays a list.

This still serves your mission. You need to review your own work and an agent’s work against tests you can trust. If the next move is upload, the real model, and citations, those parts were never forced by a new failure. If the leftover cases became tests all at once, you are back to imagined behaviour. Either way you cannot say which part of the tracer is now safe.

Go back to one test

Kent Beck’s last step of the loop is: until the list is empty, go back to writing one concrete test. You already practised that move for the first item. The second time is the same move, with one extra duty: the tests you already had must keep passing.

Until the list is empty, go back to #2 Kent Beck, “Canon TDD,” 2023 — step 5, after “Write a Test” and “Make it Pass.”

Which item you pick matters. Beck calls picking the next test a skill that comes with experience. You do not need that whole skill yet. The starter rule is: look at the tracer you already named. Which observation still has no failing test? That is next. Distant cases on the list wait.

Matt Pocock’s rule for coding agents is the same loop as a cycle: one test, one implementation, repeat. Each cycle responds to what the last cycle taught you. After a stub that returns “I don’t know,” the agent has not learned that the page works, only that the API does. The next test should ask about the page, not about upload.

Beck treats a later tidy-up as optional. Fowler treats skipping it as a common way to get the loop wrong. Pocock’s /tdd skill parks tidy-up in review, not in this cycle. That step is a later lesson. Until you have Beck’s book, Canon TDD is the free first-party source. Test Driven Development, Fowler.

Handbook Ask, three ways to continue

You have watched POST /api/ask fail, then pass with a stub that returns “I don’t know.” The tracer was: an employee pastes a question about the one PDF in SQL and sees “I don’t know” on the real page. The API test did not force the page. Compare three ways to continue:

  1. Write tests for upload, citations, history, and OpenAI errors. Then implement until they pass.
  2. Wire OpenAI, add upload and citations. The stub test is green, so the path is “proven.”
  3. Write one new test: submitting a question on the page shows “I don’t know.” Run it and confirm it fails. The existing API test stays green. Then write only enough UI to make the new test pass.

Option 1 is the mistake from lesson 0003, arriving one cycle later. The leftover cases are still a list. Turning them into tests now checks imagined behaviour again. An agent short of context may change those tests instead of growing the path.

Option 2 is the mistake from lesson 0004, arriving one cycle later. The first test never asked for upload or the real model. You have not observed the page. An agent that does this will look busy and still leave you unable to say what is safe.

Option 3 is the loop for this lesson. The tracer named the page. The page still has no failing test. That is the next item. Auth, SQL, upload, citations, and the real model stay on the list unless this new test fails without them.

[Fact]
public async Task Ask_page_shows_i_dont_know()
{
    var page = await client.GetAsync("/");
    // submit the question on the page; read the result
    Assert.Contains("I don't know", body);
}

The existing API test does not change. If the new test fails because there is no page yet, that is a real failure. After you add a thin page that posts to the stub and shows the answer, the new test should pass, and so should the old one. The stub from lesson 0002 is still allowed: this test does not require the real model.

Practice: classify

For each way of continuing after the first pass, choose whether it is the rest of the list as tests, the rest of the feature, or the next failing test. You will get feedback immediately.

The stub test is green. Write tests for upload, citations, history, and OpenAI errors. Then implement until they pass.

The stub test is green. Wire OpenAI, add upload and citations, and ship the “real” path.

The stub test is green. One new test: the page shows “I don’t know” after submit. Confirm it fails. Leave upload on the list.

Scratch list: page, unauthenticated, empty question. Turn only “page shows I don’t know” into a failing test. Existing tests stay green.
