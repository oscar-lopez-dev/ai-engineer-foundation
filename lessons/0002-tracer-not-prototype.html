Lesson 0002 · Engineering with coding agents

A tracer you keep, not a prototype you throw

Two kinds of small work look similar. A prototype answers a question and is thrown away. A tracer is a thin path through the real product. You keep the tracer and add to it later.

You can already tell a layer from a slice. The next distinction is between three things that all feel like “starting small”: a notebook experiment, an API with no user interface, and a first product ticket. Only the last of these is a path you will keep in the product.

Correct this Wrong: any small start is progress on the product.
Right: a prototype answers a question and is then thrown away. A tracer is lean, complete, and stays in the product.

This still serves Group 0 of your mission. You want to ship an AI-enabled product and direct agents so their output can be checked. An agent will often polish throwaway code until it looks finished, or build a whole feature at once. You have to say which kind of small work you want.

Two kinds of small

Hunt and Thomas split them cleanly. A prototype is for your learning — one aspect, often not even through your code:

Prototypes by their nature are not designed to be long lasting code. Prototypes are designed to be thrown away. They’re one-offs. … A prototype is like a town in a western movie. It’s all facade. There’s nothing behind it. You cannot move in and raise a family in one of those houses. Andy Hunt & Dave Thomas, interviewed by Bill Venners, 2003

A tracer is different. Hunt and Thomas describe it as a thin line of execution that you run under real conditions so you can see the result, then adjust. Their first tracer is a “Hello, world” that still goes from the user interface through logic to a database. You keep that line in the product and add to it. You do not replace it with a rewrite of throwaway prototype code.

The book line, when you have a copy: prototyping generates disposable code; tracer code is lean but complete and forms part of the skeleton of the final system. The Pragmatic Programmer, Hunt & Thomas. Until then the interview is the free first-party source.

Handbook Ask, three first moves

Same product: employees query uploaded policy PDFs. Next.js, ASP.NET Core, SQL, a model. Three “small starts” arrive:

  1. A Python notebook that sends one PDF page to the model and prints an answer.
  2. POST /api/ask that calls OpenAI. No page. “We’ll wire the UI later.”
  3. An authenticated employee pastes a question about the one PDF already in SQL and sees a short answer, or “I don’t know,” on the real page.

The notebook is a prototype. The unknown is “can the model ground in this PDF?” Hunt: you might not even go through your code. Capture the verdict (yes, no, only with the first three pages, hallucinates clause numbers). Delete or park the notebook off main. Pocock’s /prototype is this: throwaway from day one, no polish, the answer is what survives.

The endpoint with no page is a layer. It is not a prototype (you are not answering a design question) and not a tracer (nobody can walk the path). Leaving the user interface “until later” delays the integration the tracer was meant to check.

The third option is a tracer. It is valuable and testable, and you keep it: that page, API, and database row are the start of the product. The model call on that path may be a stub that always returns “I don’t know.” That is still a tracer, because you kept the path. Whether the model can ground in the PDF is a separate prototype question, answered outside the product.

Pocock’s article on tracer bullets for agents applies the same split. Models tend to build more than you asked for. Ask for one end-to-end slice, get feedback, then the next slice — not several screens and a complete API at once.

The fat “slice”

After lesson 0001 you might write this and think you are done:

Employees can upload many PDFs, ask questions with citations, see chat history, and admins can manage the corpus.

That names people and outcomes. It is still not a tracer. An agent given that prompt will try to build a whole product that does not exist yet. Hunt and Thomas’s point is that when you are still learning the target, you run one thin path you can observe, not every feature at once. Bound it: one actor, one PDF, one question, one named failure, and an explicit out-of-scope list.

Rewrite it as one tracer you would keep. Name who acts, what they see, one bound, and what is out of scope. Do not write a notebook.
