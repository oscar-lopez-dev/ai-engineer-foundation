Lesson 0001 · Engineering with coding agents

A vertical slice, not a layer

The unit of work is a thin path a user can walk. It is not a table, an endpoint, or a component on its own.

In ticket-guided work, progress is often counted as finishing a technical piece: “add the documents table,” “add POST /api/ask,” “build the form.” Each of those tickets can be merged. None of them, by itself, is a result a user can see. That is the idea this lesson replaces.

Correct this Wrong: a ticket describes a layer of work; done means that layer exists.
Right: a ticket describes a thin path a person can walk; done means that path is observable.

This is the first skill in Group 0 of your mission. You want to design and ship AI-enabled products, and to direct coding agents so their output can be checked. Agents fail in the same way ticket-guided teams fail: they finish one technical layer at a time, then find that the layers do not connect into a path a user can walk. Pocock uses the word slop for that kind of output — generated work that looks complete but is not verifiable.

The cake

Bill Wake, writing the original INVEST criteria for stories, used a cake:

Think of a whole story as a multi-layer cake, e.g., a network layer, a persistence layer, a logic layer, and a presentation layer. When we split a story, we’re serving up only part of that cake. We want to give the customer the essence of the whole cake, and the best way is to slice vertically through the layers. Developers often have an inclination to work on only one layer at a time (and get it “right”); but a full database layer (for example) has little value to the customer if there’s no presentation layer. Bill Wake, “INVEST in Good Stories, and SMART Tasks,” 2003

Wake’s other letters matter later. For this lesson, keep two: valuable (someone can use this path) and testable (you could write a check for it).

A path through your stack

Imagine Handbook Ask: employees query uploaded policy PDFs. Next.js in the browser, ASP.NET Core behind it, SQL for documents, a model call for the answer. Four tickets arrive:

  1. Create HandbookDocuments and the EF Core context.
  2. Add POST /api/ask with validation.
  3. Build AskForm.tsx with a spinner.
  4. Wire the OpenAI client.

Those are four layers. After all four are merged, you still do not know whether an employee can ask a question and see an answer. The risk that the pieces will not connect was left until the end. Hunt and Thomas designed tracer bullets to avoid that: a thin line of execution from the user interface through logic to the database. The code is production quality, but it only covers that one path.

One slice instead:

An authenticated employee can paste a question about one uploaded PDF and see either a short answer grounded in that PDF, or the explicit sentence “I don’t know.”

That slice still touches SQL, the API, the page, and the model. It does not finish any of those layers. It is valuable (someone can use it) and testable (you can watch it happen). Pocock’s /to-tickets insists on the same shape for agent work: a narrow complete path through schema, API, UI, and tests; demoable alone; sized to one context window.

Reference: vertical slice — keep this beside you when you write tickets or prompts.

A name collision (for later)

Jimmy Bogard’s “Vertical Slice Architecture” is about how code is organised in folders (by feature, not by technical layer). That is useful later. It is not the skill in this lesson. Here, “slice” means the unit of delivery: a path a person can walk.

Practice: rewrite

This is the ticket you would once have received — and the prompt you might still give an agent:

Add POST /api/ask that accepts {question} and calls OpenAI.

Rewrite it as one vertical slice for Handbook Ask. Name who acts, what they see, and one bound (one document, one failure, or an explicit out-of-scope).
